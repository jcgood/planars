# coding/ package structure

`coding/` contains the coordinator tooling:
- `__main__.py`: `python -m coding <command> [options]` dispatch. Every command module exposes `build_parser() -> argparse.ArgumentParser` (Phase 5 unit A/B, issue #271) separately from `main(args: argparse.Namespace | None = None) -> None` — `main()` parses `sys.argv` itself only when called with no `args`, so every existing test that monkeypatches `sys.argv` and calls `mod.main()` still works unchanged. `__main__.py`'s dispatch builds the parser, parses once, and calls `preconditions.enforce(op_id, args)` (Phase 5 unit D) then `provenance.record(cmd, op_id, args)` (Phase 5 unit E) before `mod.main(args)` directly instead of re-parsing inside the command — this is the chokepoint both units hook into, keyed by the command name and its already-parsed `args`. Both units D and E are done. `restructure_sheets.py`/`sync_params.py` (hand-rolled colon/comma flag parsers) and `check_codebook.py`/`setup_root_folder.py` (no flags at all) still fit the same contract — the former's `build_parser()` exists for `--help` and unknown-flag detection while the tested colon/comma helpers still read `sys.argv` directly for values, the latter's `build_parser()` returns an empty parser. `registry.py` is the module list this file used to hand-maintain in its own docstring, now derived instead.
- `gating.py`: `flag_dest(flag)`/`gate_satisfied(apply_gate, mode_name, args)` — the one piece of gate-matching logic `preconditions.py` and `provenance.py` both need (does a record's or mode's `apply_gate` match the real args of an invocation), factored out so it isn't duplicated between them. Handles the ordinary case (space-separated `--flag` list, all must be set) and the null case (a mode with no `--apply` concept, active on its own flag alone); falls back to "always active" for a gate stated as prose rather than real flag syntax (`apply_pending`'s `apply_gate` is "interactive (per-entry approval, not a single --apply flag)", since which entries get applied depends on runtime `input()` prompts, not anything in `args`) — the safer failure mode for provenance logging, where over-logging beats silently missing a real write.
- `preconditions.py`: Centralized precondition enforcement (Phase 5 unit D, issue #271) — `active_preconditions(op_id, args)`/`enforce(op_id, args)`, called from `__main__.py`'s dispatch chokepoint right after parsing, before the command's own `main()` runs. Derives which preconditions apply to a real invocation directly from that command's `data_dependency_schema/operations.yaml` record (its base `apply_gate` plus any active `modes`, matched via `gating.py`), so a precondition declared there can no longer go silently unchecked the way Findings 23/24 twice found (`docs/data-layer-progress.md`) — the declaration IS what runs, not a separately hand-written call. Only `coded_data_clean_tree` is enforced here — it replaced the scattered manual `drive._check_coded_data_clean()` calls previously in `generate_sheets.py`/`import_sheets.py`/`prune_manifest.py`/`restructure_sheets.py`/`sync_diagnostics_yaml.py`/`sync_params.py`/`update_sheets.py` (migrated file-by-file, per Jeff's decision on the unit D open question). `coded_data_git_identity_configured` and `check_notes_documents_scope_authorized` stay enforced where they already were (inside `drive._autocommit_data()`, and a manual one-time OAuth step, respectively) — neither was a "`_check_coded_data_clean()`-style call", the shape this unit was scoped to replace, so centralizing them would be a different, unscoped change.
- `provenance.py`: Provenance capture (Phase 5 unit E, issue #271) — `writes_to_drive(op_id, args)`/`record(cli_command, op_id, args)`, called from `__main__.py`'s dispatch chokepoint right before the command's own `main()` runs (so a run that fails partway through is still logged — a partial failure can still have written something). Appends one JSON line (`{timestamp, command, args}`) to `provenance_log.jsonl` at the repo root (gitignored, append-forever per Jeff's decision on the unit E open question) whenever the actual invocation reaches a Drive/Sheets/Docs write, derived from each command's `operations.yaml` `writes_to_drive` field (base + `modes`, matched via `gating.py`) — not every `--apply` run regardless of what it touched, and not every command (read-only ones like `integrity-check`/`capture-drive-state` are never logged). `apply_pending` is never logged even though it performs destructive changes: its own direct Drive footprint is a read-only lookup, and the actual writes are delegated to a subprocess call to another `python -m coding ... --apply`, which logs itself independently. Known, deliberately accepted gap: `import-sheets` paints pink highlighting on invalid cells on every run including a dry run, a real Sheet write not gated by `--apply` the way its other side effects are — its `operations.yaml` `apply_gate` describes those other effects correctly, so a dry run that paints cells isn't logged. See the module docstring for why this wasn't special-cased.
- `drive.py`: Shared Drive/Sheets client helpers — OAuth2 auth, config load/save, manifest upload/download, `_with_retry(fn)` for 429/500/503 backoff, `_autocommit_data()` (commit+push writes to `coded_data/`), and `_check_coded_data_clean()` (abort if `coded_data/` has uncommitted changes matching given extensions — refuses to let a command act on a partially-written/reverted state; called by `import_sheets.py`, `update_sheets.py`, `sync_params.py`, and `generate_sheets.py --regen-dependents` before any of them read or write `coded_data/`. Centralized here after issue #248's stray-row incident, where `update-sheets` had no such guard and wrote bogus rows to 16 live sheets from a `planar_{lang_id}.tsv` left stale by an earlier step's failed auto-commit). Also home to three shared helpers that collapsed issue #276's duplicated Drive-sharing/creation code: `ensure_anyone_permission(doorway, file_id, role="reader")` (grants "anyone with the link" unless one already exists — the single check that makes it safe to call unconditionally on every run: a manually-revoked share self-heals, a normal repeat run never piles up a duplicate), `create_or_update_shared_file(doorway, content, filename, mimetype, folder_id, existing_file_id=None, role="reader")` (create-or-update with rename-on-update, calling `ensure_anyone_permission` internally — used by `generate_notebooks.py` and `generate_reports.py`, whose per-file uploaders were identical once sharing timing was unified), and `get_or_create_spreadsheet(doorway, folder_id, name)` (find-by-name-in-folder or create — used by `generate_status_sheet.py` and `generate_biuniqueness_allomorphy_sheet.py`, whose per-file copies were identical). The old hardcoded, uncollapsed sharing helpers `_share_anyone_with_link`, `_share_with_person`, and `_remove_anyone_permission` were dead code (no remaining callers once the doorway migration finished — every caller that used to reach them directly now goes through the doorway instead) and were deleted rather than folded in — see `docs/data-layer-progress.md`'s decisions log. `upload_manifest()` checks the config it's about to write against `manifest_contract.check()` (Phase 6 boundary 4, issue #271) and prints a warning if it finds anything, but writes regardless — deliberately non-blocking; see `manifest_contract.py`'s module docstring and `docs/data-layer-progress.md`'s 2026-08-17 decisions-log entry for why.
- `manifest_contract.py`: pydantic data contract for the Drive manifest (Phase 6 boundary 4, issue #271) — the plan's fourth candidate boundary, and the odd one out: dict/JSON, not a DataFrame, so pydantic rather than the pandera `planars/contracts.py` and `contracts.py` use. Far more permissive than the other three boundaries and never raises — `check(full_config)` returns a list of problem strings (empty if none). `load_manifest()` is the highest-blast-radius function in the project (called by nearly every command), and this model can only be checked against one static fixture (no live Drive access before Phase 9), so every field is `Optional` and `extra="allow"` at every level — a violation means the manifest isn't shaped like `{lang_id: {...}}` at all, not merely that it carries an unrecognized field. Two callers: `drive.upload_manifest()` (warns, never blocks) and `integrity_check.py`'s `MANIFEST SHAPE` section (does let a violation drive a real, trackable `integrity-error` — safe given how permissive the model is). See the module docstring for the full reasoning.
- `drive_doorway.py`: The Drive/Sheets **doorway** — the one interface commands should use to reach Drive, Sheets, and Docs (issue #271, Phase 0a). Defines the `DriveDoorway`/`SpreadsheetHandle`/`WorksheetHandle` protocols, `GspreadDoorway` (live), and `get_doorway()`/`set_doorway()` for injection. Handle method names mirror gspread's exactly, so migrating a caller is a call-site substitution and helpers shared with unmigrated files keep working; `GspreadDoorway` therefore returns raw gspread objects as handles. `tests/fake_drive.py` is the offline implementation, seeded from `tests/fixtures/drive_state/` (recorded by `capture-drive-state`) — it makes every command testable with no network and records a mutation log for assertion. **Migrated so far: `refresh_dropdowns.py`, `generate_reports.py`, `setup_root_folder.py`, `apply_pending.py`, `prune_manifest.py`, `check_notes.py`, `generate_biuniqueness_allomorphy_sheet.py`, `sync_diagnostics_yaml.py`, `import_planar.py`, `generate_notebooks.py`, `update_sheets.py`, `generate_status_sheet.py`, `validate_coding.py`, `integrity_check.py`, `import_sheets.py`, `sync_params.py`, `generate_sheets.py`, `restructure_sheets.py`.** All commands that touch Drive now go through the doorway (`tests/test_doorway_coverage.py` derives the list and confirms it is empty — the plan's hand-written count of eleven was wrong, and the real total turned out to be eighteen). `tests/render_mutations.py` renders a mutation log into a reviewable digest (tab titles and column headers resolved instead of raw IDs) — use it for the human-review step, not the raw JSON; it cannot yet resolve headers for a spreadsheet created within the same test run (only recorded fixtures), so a creation-heavy digest like `generate_sheets`' or `restructure_sheets`' shows `BEYOND HEADER` throughout — a rendering gap, not a migration bug, confirmed by the mutation-log diff instead. `tests/mutation_checks.py` holds assertions shared across commands; so far one, `assert_no_criterion_writes_onto_trailing_columns` — no dropdown and no criterion note may land on `Source`/`Comments`. Two commands got that wrong independently (#272 and Finding 10), and `sync_params.py` — the file that inserts and deletes criterion columns most densely of any command — was checked against the same list and passes it clean: `_get_current_params`, `_insert_param_columns`, and `_build_dropdown_refresh_requests` all derive a tab's criterion columns from its own header, never from the manifest. `generate_sheets.py` was the other file flagged for this check (it builds `construction_params` and per-column dropdowns directly from the diagnostics YAML in `_create_analysis_sheet`, `_add_constructions_to_existing_sheet`, and `_regen_construction`) and also passes clean: every dropdown/note write derives its column position from the row it just built, never from a stored manifest offset. `generate_status_sheet.py` reads a same-named but unrelated local `_construction_params()` — not the manifest's — and `validate_coding.py` writes only pink highlighting built from its own local param map, so neither ever needed that assertion. `integrity_check.py`'s `_section_sheets` and `import_sheets.py`'s `_validate_tab`/`_validate_pair_tab` both also read `construction_params`, the former to *compare* it against the live header and print a warning on mismatch, the latter as the allowed-value set fed into validation — neither ever writes a dropdown or a criterion note back to Drive (`import_sheets.py`'s only sheet write is `highlight_cells`, painting backgrounds), so neither needed the assertion; see the mismatch-comparison bug recorded as a Finding in `docs/data-layer-progress.md`, unrelated to the migration itself. `restructure_sheets.py` caught a real, pre-existing bug this way (Finding 16, `docs/data-layer-progress.md`): `_copy_pair_tab_with_rename` hardcoded `col_start=4` for a re-populated pair tab, right for coreference's four-structural-column shape but wrong for nonpermutability's/phrasal_accent's two-column "general" shape, landing the dropdown on `Comments` instead of the criterion column. Confirmed identical between the unmigrated and migrated code (pre-existing, not introduced by the migration) before being fixed in a follow-up commit the same day — `col_start` is now `header.index(criterion_col)`, derived rather than assumed, matching every other column-writing function in this file.
- `registry.py`: `python -m coding registry` — the derived command inventory (Phase 5 unit C, issue #271). `build_registry()` joins two things that already exist and were never duplicated into this file: `__main__.py`'s `_COMMANDS` table plus every command module's `build_parser()` (Phase 5 units A/B — what flags a command takes) with `data_dependency_schema/operations.yaml` (Phase 4 — what a command does, its side effects, idempotency, preconditions, ordering). Recomputed fresh on every call, nothing cached, so there is nothing here that can go stale — the plan's own words for why this has to be derived rather than hand-authored: "a hand-authored registry is worse than none, because a stale map gets trusted." **That claim was false until 2026-08-18** (Phase 8, issue #271's idempotency audit): `_load_operations()` cached the parsed `operations.yaml` in a module-level global after its first read — harmless for the ordinary CLI invocation (a fresh process every time) but a real gap for anything importing this module and calling `build_registry()` more than once in the same process, which a test suite does constantly. Fixed by removing the cache; `tests/test_registry.py`'s `test_a_second_call_in_the_same_process_reflects_a_changed_operations_yaml` proves it directly (writes a real file, calls twice, changes the file in between, confirms the second call sees the change) rather than trusting the docstring. Plain listing by default (`cli_command` + `operations.yaml`'s `description`, one per line); `--command CLI_COMMAND` for one command's full detail (flags, side effects, idempotency, preconditions, whether it writes to Drive, ordering constraints, modes). Replaced `__main__.py`'s own hand-maintained "Commands:" docstring table, which was exactly the kind of duplicated inventory this command exists to remove.
- `capture_drive_state.py`: Records live Drive state (spreadsheets + manifest) to `tests/fixtures/drive_state/`. **Read-only** — the only live Drive call permitted before Phase 9 of the data layer plan. Never normalise or hand-edit the fixtures; re-run the capture instead.
- `refresh_dropdowns.py`: Refreshes criterion dropdown validation on existing sheets without touching annotation data (`--apply`, `--lang`); reads criterion columns from the tab's own header and values from the diagnostics YAML, never the manifest (issue #272's fix — see `_resolve_criterion_columns`/`_fresh_param_values`). Its manifest write now goes through `drive.upload_manifest`, the same shared writer `generate_sheets.py`, `sync_params.py`, `update_sheets.py`, `import_sheets.py`, and `restructure_sheets.py` already use, instead of an inline `doorway.update_file` call with no key-reordering and no create-if-missing fallback — closing the gap where a lost `_planars_config_file_id` meant it gave up with a `[WARNING]` instead of creating a fresh manifest.json like every other writer (issue #276).
- `schemas.py`: Cached loaders for `load_diagnostic_classes()` and `load_diagnostic_criteria()`; `languages.yaml` excluded (read fresh by callers).
- `make_forms.py`: `build_element_index`, `_read_diagnostics_for_language` — utilities used by other scripts. Also provides `resolve_keystone_active` and `resolve_keystone_na_criteria`. Handles `construction_criteria` — emits one TSV row per construction for classes that use it. `build_element_index`'s Position/Class_Type validation is enforced via the pandera schemas in `contracts.py` (Phase 6 of the data layer redesign, issue #271), not inline `if`/`raise` blocks; it catches `pandera.errors.SchemaError` and re-raises `ValueError` so its three callers (`generate_sheets.py`, `update_sheets.py`, `restructure_sheets.py`) see the exception type they always have.
- `contracts.py`: pandera data contracts for `make_forms.py`'s planar-load boundary (Phase 6 of the data layer redesign, issue #271, second of four candidate boundaries — see `planars/contracts.py` for the first). `position_integer_schema()` and `class_type_schema()`. See the module docstring for the two-stage narrowing this reproduces and why the duplicate-key check stays procedural.
- `generate_sheets.py`: Creates annotation sheets; validates planar/diagnostics first; **dry-run by default — the base (sheet-creation) command requires `--apply` to write anything to Drive** (`_plan_language_creation` computes what would be created from already-fetched manifest data, no live Drive calls needed for the dry-run report itself). This was a gap until this convention was regularized: unlike every other mutating command in the project, `generate-sheets` previously had no dry-run/apply distinction at all and always wrote live — fixed after an accidental live-sheet creation surfaced the inconsistency with `docs/tooling-design.md`'s "dry-run by default" principle. `--regen-construction` and `--regen-dependents` are separate code paths, unaffected by `--apply` — they always act live, gated by their own guards instead (see below). **`--force` aborts if any language already has sheet IDs in the manifest** (annotation data is irreplaceable); each spreadsheet gets a `Status` tab with `in-progress`/`ready-for-review` dropdowns. Supports two-stage pair-sheet workflows for **nonpermutability** (`element_prescreening` first, then `--regen-construction nonpermutability:general`) and **coreference** (`prescreening` first, then `--regen-construction coreference:reflexivization` etc. for each pair construction). Both prescreening filters (`_filter_nonperm_pairs_by_prescreening`'s `scopal`, `_filter_reflex_pairs_by_prescreening`'s `referential`) exclude an element **by name, across every structural position**, not just at the one position marked `n` — an unresolved linguistics question (is the criterion a property of the element globally, or of the element at a position?), not a bug to silently pick a side of. Both now share `_abort_if_criterion_diverges_by_position`, which aborts and files/updates a `diagnostics` GitHub issue when an element is marked `n` at one position and `y`/`both` at another, rather than resolving it either way. First built for `scopal` (issue #228); `referential` didn't get the same guard until issue #285 found the gap — #228's own text had incorrectly assumed coreference was unaffected. `_regen_dependents_simple` runs automatically during `data-refresh`, gated by `coded_data_clean_tree` first (enforced centrally — see `preconditions.py`'s entry above) — but only ever regenerates a dependent tab that doesn't exist yet (nothing to lose), never one with existing content, so it can't hit the guard below. Pass `--pos-remap OLD_NUM:NEW_NUM` (repeatable) when position numbers have shifted. **`--regen-construction` aborts (`_find_annotated_drops`/`_format_annotated_drop`) instead of writing if it would silently drop an annotated pair-row** — it overwrites the live Sheet immediately with no confirmation step downstream (`import-sheets` → `apply-pending` only syncs the *local* copy to match afterward, it doesn't gate the write). Run `restructure-sheets --split-element`/`--rename-element` first if the element was renamed or split (clears the guard naturally, since the old rows are already gone from the Sheet by the time `--regen-construction` runs — no need to remember command order), or pass `--confirm-drop` if the drop is a genuine scope change, not data loss. See issue #241. **`--regen-construction` snapshots the tab's current live content to `regen_snapshots/{lang}_{class}_{construction}.json` (gitignored) immediately before clearing and rewriting it** (`_snapshot_before_regen`, issue #271 — a Phase 7 follow-up, found while checking whether `import-sheets`/`generate-sheets` needed the same crash-recovery treatment as `restructure-sheets`'s archive-then-recreate did). This tab read exists specifically to preserve live annotator edits not yet downloaded via `import-sheets`; the clear-then-rewrite that follows is two separate Drive calls, not atomic, so a crash between them could otherwise destroy those edits with nothing to recover them from. Deliberately a plain snapshot, not a `restructure_journal.py`-style resume/rollback system — re-running `--regen-construction` after any interruption already recovers cleanly on its own (it recomputes the pair list fresh from source data every time), so there is nothing to "resume"; the snapshot exists purely so a coordinator or Claude can check by hand whether anything was lost, and is overwritten (not appended) each run. Migrated to the Drive doorway — the largest file migrated so far (2,654 lines) and the first whose migration was not a plain call-site substitution in `main()`/one leaf helper: `gc`/`drive` were threaded as explicit parameters through this file's own call chain (`_create_or_update_tsv_sheet` → `_upload_lang_setup_as_sheets`, `_create_analysis_sheet`, `_regen_construction` → `_regen_dependents_simple`), so the migration replaced two parameters with one (`doorway`) at every level. `_add_constructions_to_existing_sheet` needed no signature change at all — it already took an open spreadsheet handle rather than a client, since `update_sheets.py` (which also calls it) reaches Drive through the doorway with no client to hand over. `_regen_construction`'s spreadsheet open now retries where it previously did not (opening is an idempotent read, so this changes nothing about what gets written) — see `docs/data-layer-progress.md`'s decisions log. **`--apply` used to skip a language's existing-class-new-construction scan whenever that language also had a brand-new class with no sheet at all** — the scan only ran inside the `if not new_class_names` branch, so a class that already had a sheet but gained a construction in its diagnostics YAML was silently left behind on any run that also created a new class sheet. Found onboarding arao1248's `nonpermutability`/`free_occurrence` classes (2026-08-10) when its unrelated `subspanrepetition` construction addition stopped showing up in the same run. Fixed by running the scan unconditionally over every already-existing class, independent of `new_class_names`. **All 8 of this file's structural doorway calls (`create_spreadsheet` ×2, `move_file` ×2, `create_permission` ×3, `get_or_create_folder` ×1) are now wrapped in `_with_retry`** (issue #284, 2026-08-19) — the same gap `restructure_sheets.py` had before its Phase 8 fix. **`_regen_dependents_simple` now returns the list of (language, dependent construction) failures instead of `None`, and `--regen-dependents` exits non-zero if that list is non-empty** (issue #283, 2026-08-19) — a per-language regeneration failure was already caught and printed, but otherwise vanished with no way for the caller (or the daily automation) to know anything had gone wrong; `data-refresh.yml` now files/closes a `regen-dependents-error` issue keyed on the exit code. One failure still doesn't stop the loop from trying the rest — that per-item resilience is this function's whole contract, unchanged.
- `update_sheets.py`: Adds missing rows/trailing columns to existing sheets; ensures Status tab exists and is last. Also detects and creates new construction tabs for constructions in the diagnostics YAML not yet in the manifest; updates the manifest on Drive. `--apply` aborts if `coded_data/` has uncommitted changes before reading the planar (`coded_data_clean_tree`, enforced centrally — see `preconditions.py`'s entry above). Which columns of a tab hold criteria, how wide an added row should be, and what each dropdown allows all come from the tab's own header plus the diagnostics YAML, via `refresh_dropdowns._resolve_criterion_columns`/`_fresh_param_values` — never from the manifest, which is bookkeeping and goes stale. When the two can't be reconciled the tab is skipped with a reason rather than written to. Before this, appending one row narrowed the whole tab's dropdowns to `y`/`n` and a keystone row could write `NA` into `Source`/`Comments` (see `docs/data-layer-progress.md` § Findings 9–11).
- `sync_params.py`: Syncs criterion columns when `diagnostics_{lang_id}.yaml` changes; supports rename, split, merge, remove; regenerates YAML afterward. `coded_data_clean_tree` is enforced centrally before `--apply` reads diagnostics/planar TSVs (see `preconditions.py`'s entry above). Migrated to the Drive doorway; the tab's own header — never the manifest — decides which columns are current, new, or surplus. Before a fix found while migrating (Finding 14, `docs/data-layer-progress.md`), adding or removing a column re-stamped the manifest's record of *every* criterion in that construction with the fresh diagnostics values, including ones whose dropdown was never touched on the sheet, so a widened value on an untouched criterion could go stale on the sheet forever without `--refresh-dropdowns` ever reporting it. Each construction's `param_values` now only ever gets the keys a given run actually pushed to the sheet.
- `sync_diagnostics_yaml.py`: Syncs YAML → TSV (default), YAML → Sheet (`--to-sheet`), or diffs TSV → YAML (`--from-tsv`) writing ambiguous differences to `diagnostics_drift.json`. `coded_data_clean_tree` (extensions `(".yaml", ".tsv")`, since this command reads/writes both) is enforced centrally at the dispatch chokepoint before any of the three `--apply` directions reads or writes `coded_data/` — see `preconditions.py`'s entry below (Phase 5 unit D, issue #271); added as a declared precondition 2026-08-11 alongside `prune_manifest.py`'s version of the same gap, found reviewing preconditions for `data_dependency_schema/operations.yaml` (issue #271 Phase 4). **The YAML → TSV and YAML → Sheet directions now exit non-zero when any language hits a blocking validation error** (issue #283, 2026-08-19) — both used to always exit 0, so a broken `diagnostics_{lang_id}.yaml` silently stopped that language's sync forever with nothing surfacing it; `data-refresh.yml` now files/closes a `diagnostics-yaml-error` issue keyed on the exit code. Fixing this surfaced a real, separate pre-existing bug: `_sync_to_sheet` gated on *every* `level == "error"`, ignoring `ValidationIssue.blocking` entirely, unlike `_sync_to_tsv`'s correct `.blocking`-filtered gate — so a non-blocking error (a required class not yet drafted, e.g. arao1248's `proform`, issue #279) was silently withholding the Sheet push it was explicitly designed not to withhold. Harmless while invisible either way; would have manufactured a daily false-alarm issue for a known, already-tracked gap the moment the exit code was wired up, so fixed in the same change rather than after. `_sync_from_tsv` (the third direction) is unaffected — its ambiguous items already have their own visible path via `diagnostics_drift.json` and the `diagnostics-drift` issue.
- `sync_qualification_hashes.py`: Stamps `qualification_rule_hash` in `diagnostic_classes.yaml` after module review; run as the final step of the qualification rule update workflow.
- `generate_rule_update_prompt.py`: Generates a coordinator-facing Claude prompt for each class with a missing or stale `qualification_rule_hash`; used by `data-refresh.yml` to enrich `codebook-error` issue bodies.
- `restructure_sheets.py`: Archives and regenerates sheets after structural changes; `--rename-map` (positions), `--rename-element` (elements), `--split-element old:new1,new2,...` (retires one element into several finer-grained replacements within the same position; new rows get a Comments breadcrumb pointing back to the archived sheet if the old element had data), `--rename-class` (archives old sheet, creates new, renames local TSV dir, updates manifest); pair with `prune-manifest` if retiring rather than renaming. On `--apply`, after a language's sheets actually change, notifies that language's tracking issue via `notify.py` (stdout doesn't reach collaborators — see `notify.py`'s docstring), and pushes `planar_{lang_id}.tsv` back to the Drive planar spreadsheet via `import_planar.push_planars_to_sheets()` so the master Sheet doesn't go stale (issue #248). `--split-element` also cascades into every `row_type: pair_rows` construction referencing the retired element (`_apply_split_to_pair_rows`, `_pair_construction_criterion`) — found generically via `_get_pair_row_constructions()`, not hardcoded per class — fanning each old pair-row into one blank new row per replacement element, with the old criterion value/Source/Comments quoted verbatim into the new row's Comments cell (never pre-filled as a live default: policy resolved on issue #241, see #262 for why). A self-pair on the retired element is flagged for manual review rather than guessed at. Migrated to the Drive doorway — the last of the eighteen files, deliberately: the archive-then-rebuild command behind #248's original incidents. **`--resume`/`--rollback` (Phase 7, issue #271, 2026-08-17)** recover from a run interrupted mid-class: `coding/restructure_journal.py` journals each class's progress through archive → create → manifest-sync to `restructure_journal.json` (gitignored) before each Drive-mutating step, and any run — including a plain `--apply` — refuses to start new work while the journal is non-empty, reporting exactly which class is stuck and why. `--resume` finishes a class whose replacement sheet already exists (pure manifest bookkeeping, no further Drive-sheet mutation) or, for a class where only the old sheet was archived and nothing yet replaced it, undoes that archive and lets the ordinary loop redo it cleanly this run — then continues restructuring normally. `--rollback` undoes only that same safe case and then stops, refusing outright if any stuck class has already gotten past archiving (a real replacement sheet with carried-over annotation data exists by then, and rollback will not delete it — only `--resume` is offered for that case).
