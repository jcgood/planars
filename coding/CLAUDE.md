# coding/ package structure

`coding/` contains the coordinator tooling:
- `drive.py`: Shared Drive/Sheets client helpers — OAuth2 auth, config load/save, manifest upload/download, `_with_retry(fn)` for 429/500/503 backoff, `_autocommit_data()` (commit+push writes to `coded_data/`), and `_check_coded_data_clean()` (abort if `coded_data/` has uncommitted changes matching given extensions — refuses to let a command act on a partially-written/reverted state; called by `import_sheets.py`, `update_sheets.py`, `sync_params.py`, and `generate_sheets.py --regen-dependents` before any of them read or write `coded_data/`. Centralized here after issue #248's stray-row incident, where `update-sheets` had no such guard and wrote bogus rows to 16 live sheets from a `planar_{lang_id}.tsv` left stale by an earlier step's failed auto-commit). Also home to three shared helpers that collapsed issue #276's duplicated Drive-sharing/creation code: `ensure_anyone_permission(doorway, file_id, role="reader")` (grants "anyone with the link" unless one already exists — the single check that makes it safe to call unconditionally on every run: a manually-revoked share self-heals, a normal repeat run never piles up a duplicate), `create_or_update_shared_file(doorway, content, filename, mimetype, folder_id, existing_file_id=None, role="reader")` (create-or-update with rename-on-update, calling `ensure_anyone_permission` internally — used by `generate_notebooks.py` and `generate_reports.py`, whose per-file uploaders were identical once sharing timing was unified), and `get_or_create_spreadsheet(doorway, folder_id, name)` (find-by-name-in-folder or create — used by `generate_status_sheet.py` and `generate_biuniqueness_allomorphy_sheet.py`, whose per-file copies were identical). The old hardcoded, uncollapsed sharing helpers `_share_anyone_with_link`, `_share_with_person`, and `_remove_anyone_permission` were dead code (no remaining callers once the doorway migration finished — every caller that used to reach them directly now goes through the doorway instead) and were deleted rather than folded in — see `docs/data-layer-progress.md`'s decisions log.
- `drive_doorway.py`: The Drive/Sheets **doorway** — the one interface commands should use to reach Drive, Sheets, and Docs (issue #271, Phase 0a). Defines the `DriveDoorway`/`SpreadsheetHandle`/`WorksheetHandle` protocols, `GspreadDoorway` (live), and `get_doorway()`/`set_doorway()` for injection. Handle method names mirror gspread's exactly, so migrating a caller is a call-site substitution and helpers shared with unmigrated files keep working; `GspreadDoorway` therefore returns raw gspread objects as handles. `tests/fake_drive.py` is the offline implementation, seeded from `tests/fixtures/drive_state/` (recorded by `capture-drive-state`) — it makes every command testable with no network and records a mutation log for assertion. **Migrated so far: `refresh_dropdowns.py`, `generate_reports.py`, `setup_root_folder.py`, `apply_pending.py`, `prune_manifest.py`, `check_notes.py`, `generate_biuniqueness_allomorphy_sheet.py`, `sync_diagnostics_yaml.py`, `import_planar.py`, `generate_notebooks.py`, `update_sheets.py`, `generate_status_sheet.py`, `validate_coding.py`, `integrity_check.py`, `import_sheets.py`, `sync_params.py`, `generate_sheets.py`, `restructure_sheets.py`.** All commands that touch Drive now go through the doorway (`tests/test_doorway_coverage.py` derives the list and confirms it is empty — the plan's hand-written count of eleven was wrong, and the real total turned out to be eighteen). `tests/render_mutations.py` renders a mutation log into a reviewable digest (tab titles and column headers resolved instead of raw IDs) — use it for the human-review step, not the raw JSON; it cannot yet resolve headers for a spreadsheet created within the same test run (only recorded fixtures), so a creation-heavy digest like `generate_sheets`' or `restructure_sheets`' shows `BEYOND HEADER` throughout — a rendering gap, not a migration bug, confirmed by the mutation-log diff instead. `tests/mutation_checks.py` holds assertions shared across commands; so far one, `assert_no_criterion_writes_onto_trailing_columns` — no dropdown and no criterion note may land on `Source`/`Comments`. Two commands got that wrong independently (#272 and Finding 10), and `sync_params.py` — the file that inserts and deletes criterion columns most densely of any command — was checked against the same list and passes it clean: `_get_current_params`, `_insert_param_columns`, and `_build_dropdown_refresh_requests` all derive a tab's criterion columns from its own header, never from the manifest. `generate_sheets.py` was the other file flagged for this check (it builds `construction_params` and per-column dropdowns directly from the diagnostics YAML in `_create_analysis_sheet`, `_add_constructions_to_existing_sheet`, and `_regen_construction`) and also passes clean: every dropdown/note write derives its column position from the row it just built, never from a stored manifest offset. `generate_status_sheet.py` reads a same-named but unrelated local `_construction_params()` — not the manifest's — and `validate_coding.py` writes only pink highlighting built from its own local param map, so neither ever needed that assertion. `integrity_check.py`'s `_section_sheets` and `import_sheets.py`'s `_validate_tab`/`_validate_pair_tab` both also read `construction_params`, the former to *compare* it against the live header and print a warning on mismatch, the latter as the allowed-value set fed into validation — neither ever writes a dropdown or a criterion note back to Drive (`import_sheets.py`'s only sheet write is `highlight_cells`, painting backgrounds), so neither needed the assertion; see the mismatch-comparison bug recorded as a Finding in `docs/data-layer-progress.md`, unrelated to the migration itself. `restructure_sheets.py` caught a real, pre-existing bug this way (Finding 16, `docs/data-layer-progress.md`): `_copy_pair_tab_with_rename` hardcoded `col_start=4` for a re-populated pair tab, right for coreference's four-structural-column shape but wrong for nonpermutability's/phrasal_accent's two-column "general" shape, landing the dropdown on `Comments` instead of the criterion column. Confirmed identical between the unmigrated and migrated code (pre-existing, not introduced by the migration) before being fixed in a follow-up commit the same day — `col_start` is now `header.index(criterion_col)`, derived rather than assumed, matching every other column-writing function in this file.
- `capture_drive_state.py`: Records live Drive state (spreadsheets + manifest) to `tests/fixtures/drive_state/`. **Read-only** — the only live Drive call permitted before Phase 9 of the data layer plan. Never normalise or hand-edit the fixtures; re-run the capture instead.
- `refresh_dropdowns.py`: Refreshes criterion dropdown validation on existing sheets without touching annotation data (`--apply`, `--lang`); reads criterion columns from the tab's own header and values from the diagnostics YAML, never the manifest (issue #272's fix — see `_resolve_criterion_columns`/`_fresh_param_values`). Its manifest write now goes through `drive.upload_manifest`, the same shared writer `generate_sheets.py`, `sync_params.py`, `update_sheets.py`, `import_sheets.py`, and `restructure_sheets.py` already use, instead of an inline `doorway.update_file` call with no key-reordering and no create-if-missing fallback — closing the gap where a lost `_planars_config_file_id` meant it gave up with a `[WARNING]` instead of creating a fresh manifest.json like every other writer (issue #276).
- `schemas.py`: Cached loaders for `load_diagnostic_classes()` and `load_diagnostic_criteria()`; `languages.yaml` excluded (read fresh by callers).
- `make_forms.py`: `build_element_index`, `_read_diagnostics_for_language` — utilities used by other scripts. Also provides `resolve_keystone_active` and `resolve_keystone_na_criteria`. Handles `construction_criteria` — emits one TSV row per construction for classes that use it.
- `generate_sheets.py`: Creates annotation sheets; validates planar/diagnostics first; **dry-run by default — the base (sheet-creation) command requires `--apply` to write anything to Drive** (`_plan_language_creation` computes what would be created from already-fetched manifest data, no live Drive calls needed for the dry-run report itself). This was a gap until this convention was regularized: unlike every other mutating command in the project, `generate-sheets` previously had no dry-run/apply distinction at all and always wrote live — fixed after an accidental live-sheet creation surfaced the inconsistency with `docs/tooling-design.md`'s "dry-run by default" principle. `--regen-construction` and `--regen-dependents` are separate code paths, unaffected by `--apply` — they always act live, gated by their own guards instead (see below). **`--force` aborts if any language already has sheet IDs in the manifest** (annotation data is irreplaceable); each spreadsheet gets a `Status` tab with `in-progress`/`ready-for-review` dropdowns. Supports two-stage pair-sheet workflows for **nonpermutability** (`element_prescreening` first, then `--regen-construction nonpermutability:general`) and **coreference** (`prescreening` first, then `--regen-construction coreference:reflexivization` etc. for each pair construction). `_regen_dependents_simple` runs automatically during `data-refresh`, gated by `drive._check_coded_data_clean()` first — but only ever regenerates a dependent tab that doesn't exist yet (nothing to lose), never one with existing content, so it can't hit the guard below. Pass `--pos-remap OLD_NUM:NEW_NUM` (repeatable) when position numbers have shifted. **`--regen-construction` aborts (`_find_annotated_drops`/`_format_annotated_drop`) instead of writing if it would silently drop an annotated pair-row** — it overwrites the live Sheet immediately with no confirmation step downstream (`import-sheets` → `apply-pending` only syncs the *local* copy to match afterward, it doesn't gate the write). Run `restructure-sheets --split-element`/`--rename-element` first if the element was renamed or split (clears the guard naturally, since the old rows are already gone from the Sheet by the time `--regen-construction` runs — no need to remember command order), or pass `--confirm-drop` if the drop is a genuine scope change, not data loss. See issue #241. Migrated to the Drive doorway — the largest file migrated so far (2,654 lines) and the first whose migration was not a plain call-site substitution in `main()`/one leaf helper: `gc`/`drive` were threaded as explicit parameters through this file's own call chain (`_create_or_update_tsv_sheet` → `_upload_lang_setup_as_sheets`, `_create_analysis_sheet`, `_regen_construction` → `_regen_dependents_simple`), so the migration replaced two parameters with one (`doorway`) at every level. `_add_constructions_to_existing_sheet` needed no signature change at all — it already took an open spreadsheet handle rather than a client, since `update_sheets.py` (which also calls it) reaches Drive through the doorway with no client to hand over. `_regen_construction`'s spreadsheet open now retries where it previously did not (opening is an idempotent read, so this changes nothing about what gets written) — see `docs/data-layer-progress.md`'s decisions log.
- `update_sheets.py`: Adds missing rows/trailing columns to existing sheets; ensures Status tab exists and is last. Also detects and creates new construction tabs for constructions in the diagnostics YAML not yet in the manifest; updates the manifest on Drive. `--apply` aborts if `coded_data/` has uncommitted changes before reading the planar (see `drive.py`'s `_check_coded_data_clean()`). Which columns of a tab hold criteria, how wide an added row should be, and what each dropdown allows all come from the tab's own header plus the diagnostics YAML, via `refresh_dropdowns._resolve_criterion_columns`/`_fresh_param_values` — never from the manifest, which is bookkeeping and goes stale. When the two can't be reconciled the tab is skipped with a reason rather than written to. Before this, appending one row narrowed the whole tab's dropdowns to `y`/`n` and a keystone row could write `NA` into `Source`/`Comments` (see `docs/data-layer-progress.md` § Findings 9–11).
- `sync_params.py`: Syncs criterion columns when `diagnostics_{lang_id}.yaml` changes; supports rename, split, merge, remove; regenerates YAML afterward. `--apply` aborts if `coded_data/` has uncommitted changes before reading diagnostics/planar TSVs (see `drive.py`'s `_check_coded_data_clean()`). Migrated to the Drive doorway; the tab's own header — never the manifest — decides which columns are current, new, or surplus. Before a fix found while migrating (Finding 14, `docs/data-layer-progress.md`), adding or removing a column re-stamped the manifest's record of *every* criterion in that construction with the fresh diagnostics values, including ones whose dropdown was never touched on the sheet, so a widened value on an untouched criterion could go stale on the sheet forever without `--refresh-dropdowns` ever reporting it. Each construction's `param_values` now only ever gets the keys a given run actually pushed to the sheet.
- `sync_diagnostics_yaml.py`: Syncs YAML → TSV (default), YAML → Sheet (`--to-sheet`), or diffs TSV → YAML (`--from-tsv`) writing ambiguous differences to `diagnostics_drift.json`.
- `sync_qualification_hashes.py`: Stamps `qualification_rule_hash` in `diagnostic_classes.yaml` after module review; run as the final step of the qualification rule update workflow.
- `generate_rule_update_prompt.py`: Generates a coordinator-facing Claude prompt for each class with a missing or stale `qualification_rule_hash`; used by `data-refresh.yml` to enrich `codebook-error` issue bodies.
- `restructure_sheets.py`: Archives and regenerates sheets after structural changes; `--rename-map` (positions), `--rename-element` (elements), `--split-element old:new1,new2,...` (retires one element into several finer-grained replacements within the same position; new rows get a Comments breadcrumb pointing back to the archived sheet if the old element had data), `--rename-class` (archives old sheet, creates new, renames local TSV dir, updates manifest); pair with `prune-manifest` if retiring rather than renaming. On `--apply`, after a language's sheets actually change, notifies that language's tracking issue via `notify.py` (stdout doesn't reach collaborators — see `notify.py`'s docstring), and pushes `planar_{lang_id}.tsv` back to the Drive planar spreadsheet via `import_planar.push_planars_to_sheets()` so the master Sheet doesn't go stale (issue #248). `--split-element` also cascades into every `row_type: pair_rows` construction referencing the retired element (`_apply_split_to_pair_rows`, `_pair_construction_criterion`) — found generically via `_get_pair_row_constructions()`, not hardcoded per class — fanning each old pair-row into one blank new row per replacement element, with the old criterion value/Source/Comments quoted verbatim into the new row's Comments cell (never pre-filled as a live default: policy resolved on issue #241, see #262 for why). A self-pair on the retired element is flagged for manual review rather than guessed at. Migrated to the Drive doorway — the last of the eighteen files, deliberately: the archive-then-rebuild command with no rollback, behind #248's original incidents. `_get_or_create_subfolder` (a hand-rolled reimplementation of `drive._get_or_create_folder`, differing only in an unused `fields` mask) was consolidated into `doorway.get_or_create_folder` rather than migrated as its own function. `_lock_archived_sheet` inlines the same "list permissions, delete the `anyone` one" two-call sequence as `generate_status_sheet._lock_read_only`, since there is no doorway-level convenience for it (used by every still-unmigrated caller directly — now none). `import gspread` stays, for `gspread.utils.rowcol_to_a1` in `_cascade_rename_pair_tab` (pure coordinate arithmetic, the same reasoning as `sync_params.py`'s migration). This file never called `drive._check_coded_data_clean()` despite reading `planar_{lang_id}.tsv`/`diagnostics_{lang_id}.tsv` from `coded_data/` as its source of truth — confirmed absent, recorded as a new Finding in `docs/data-layer-progress.md` rather than fixed (adding the guard changes what the command aborts on, which is out of scope for a call-site migration). `assert_no_criterion_writes_onto_trailing_columns` caught a real, pre-existing bug here (Finding 16, fixed the same day): see the "Migrated so far" paragraph above.
- `notify.py`: Per-language GitHub issue notifications for sheet structure changes (find-or-create "Sheet updates — {lang_id}" issue, number stored in `sheets_manifest.json` as `notification_issue`; posts a comment summarizing affected sheets/folder link). Called from `restructure_sheets.py --apply`. Pure logic (`changed_lang_ids`, `get_notification_issue`, `build_first_issue_body`, `build_change_comment`) is separated from the live `gh` calls (`ensure_notification_issue`, `post_notification_comment`) for testability. Not yet wired into any GitHub Actions workflow.
- `import_planar.py`: Syncs `planar_{lang_id}.tsv` against the Drive planar spreadsheet. Default direction is Sheet → TSV (download; archives the old TSV before overwriting, writes `PLANAR_CHANGES_PATH` — `/tmp/planar_changes.json` — for the `planar-changed` issue body). Column differences are named in both directions: on the way down a column added in the Sheet is carried into the TSV, but a column the Sheet no longer has skips that language rather than blanking it locally (an absent column is far likelier to be a mistake in the Sheet than an instruction to erase — same reasoning as the empty-sheet skip). `--to-sheet` is the reverse: pushes local TSV content up to the Sheet (mirrors `sync_diagnostics_yaml.py`'s `--to-sheet`). `restructure_sheets.py --apply` calls `push_planars_to_sheets()` automatically after writing local TSVs/sheets, since it reads `planar_{lang_id}.tsv` as its source of truth but never writes it — without this, a local planar edit (e.g. via `--split-element`) goes stale the moment anyone touches the Sheet, and the next scheduled `import-planar --apply` silently reverts it (issue #248).
- `import_sheets.py`: Downloads filled annotation sheets to TSVs; auto-applies safe downstream commands; writes destructive changes to `pending_changes.json`; aborts if `coded_data/` has uncommitted changes (via `drive._check_coded_data_clean()`). Which constructions have pair rows comes from `_get_pair_row_constructions()`, i.e. from `diagnostic_classes.yaml` — same as `validate_coding.py`. It used to name the classes itself and left `phrasal_accent` out, so the two commands disagreed about one tab; see `data_dependency_schema/facts.yaml` § `pair_row_construction_set`. **Import behavior by status**: `ready-for-review` tabs are fully imported — pipeline warnings surfaced, pending changes recorded. `in-progress` tabs are imported for backup and validated (pink highlighting updated), but pipeline warnings are suppressed and structural anomalies (missing rows/columns, >10% annotated-cell decrease) raise a `collaborator-check` issue instead of going to `pending_changes.json`. Use `--ignore-status` to treat all tabs as ready-for-review.
- `apply_pending.py`: Interactive review and application of destructive changes from `import-sheets`; closes the `pending-changes` issue when cleared. For a new-construction entry it looks in the Google Sheet to see whether the tab has actually been added, rather than taking the coordinator's word for it. When it can't look, it says which of four things went wrong — no spreadsheet ID recorded on the entry, no such spreadsheet, not shared with the signed-in account, or Drive unreachable — because each needs a different next step, and only the last means "try again later". All four still let the coordinator close the entry themselves, so an entry naming a dead spreadsheet can't get stuck open.
- `prune_manifest.py`: Removes retired class entries from the Drive manifest, archives local TSVs, and moves Drive spreadsheets to `_archived/`; warns if a sheet was edited within 14 days.
- `validate.py`: Shared base — just the `ValidationIssue` dataclass.
- `validate_planar.py`: `validate_planar_df(df)` — validates planar TSV structure.
- `validate_diagnostics.py`: `validate_diagnostics_df(df, lang_id)` and `validate_diagnostics_yaml(data, lang_id)` — validate TSV and YAML forms against schema files.
- `validate_coding.py`: `validate-coding` — reads annotation sheets, validates values, updates pink highlights; exits code 1 on issues (used by the sheet-validation workflow). If a tab's header isn't the row shape its construction declares (`row_type` in `diagnostic_classes.yaml`), it says so once and checks nothing else in that tab — every value would be read from the wrong column. The message names both ways out: the `--regen-construction` command that rebuilds the sheet, and the schema field to change if the sheet is the one that's right. It still returns every row unchanged, because `import-sheets` writes whatever it's handed straight to the TSV. Before this, one mis-shaped tab produced 429 lines (issue #275). Migrated to the Drive doorway — the smallest Drive footprint of any command migrated so far (`get_doorway()`, `load_manifest()`, `doorway.open_spreadsheet()`, nothing else); `highlight_cells`/`clear_highlights` needed no edits at all, since they only call handle methods that mirror gspread by design.
- `validation_report.py`: `validation-report` — turns `validate-coding` output into a GitHub issue body for `sheet-validation.yml`. Pure parsing/formatting (the `gh` calls stay in the workflow, mirroring `notify.py`'s split). Decides three things the workflow used to get wrong: only errors and crashes warrant an issue (advisory warnings are context, never a blocker — a known recurring warning held #260 open for days); each report carries a **fingerprint** of what is wrong, so a later run reporting a *different* problem supersedes the open issue instead of commenting on it; and the reported exception line is taken from the traceback rather than from the last line of the log. Also collapses repeated messages with counts — one real run produced 429 near-identical warning lines.
- `generate_notebooks.py`: Generates per-language contributor, validation, and report notebooks, plus the coordinator notebook. Uploads (create-or-update, renamed on update, shared "anyone with the link, reader" on every run) go through `drive.create_or_update_shared_file`, shared with `generate_reports.py`'s PDF upload since the two collapsed under issue #276 — its own `_upload_file`/`_set_viewer_permissions` were deleted. That collapse surfaced a real, pre-existing bug: this file's viewer-grant reassertion had no existence check, so every regeneration (which happens after nearly every `--apply` across several commands) silently added another duplicate "anyone" permission — the same bug `setup_root_folder.py` had, just never compared side by side before. Fixed by the same `ensure_anyone_permission` check that fixes `setup_root_folder.py`.
- `generate_reports.py`: Generates and uploads `report_{lang_id}.pdf` directly (no Colab; used by nightly GitHub Action). Uses `drive.create_or_update_shared_file` for the upload (its own `_upload_pdf` was deleted) — before issue #276 this file shared its "anyone" grant only on create, so a manually-revoked report share was never restored, unlike a notebook's; both now reassert every run through the same idempotent `ensure_anyone_permission` check, so a report share self-heals too, without duplicating on a normal repeat run.
- `check_codebook.py`: Consistency check between diagnostic_criteria.yaml, diagnostic_classes.yaml, analysis modules, and diagnostics_{lang_id}.tsv.
- `integrity_check.py`: Full project-wide health report; `--lang` restricts per-language sections; `--sheets` includes live Sheets structural validation. Its DEPENDENT CONSTRUCTION STALENESS section checks pair-row constructions against their prescreening source two ways: element identity (pre-existing) and, since issue #241, position number (`_find_stale_position_cells`/`_suggest_position_remap`/`_planar_position_names`) — a pair-row can be element-identity-correct and still reference a position number superseded by a structural change elsewhere in the planar, invisible to element-set comparison alone (discovered when stan1293's coreference pairs turned out to reference pre-`v:obj-R`-insertion position numbers, apparently since the sheets were first generated). When recoverable, prints ready-to-use `--pos-remap` flags for `generate-sheets --regen-construction`. Migrated to the Drive doorway; its footprint is two independent read-only entry points (`--sheets`' spreadsheet-open/list-worksheets/read-header sequence, and `--check-manifest`'s manifest-only fast path) — no writes anywhere in the file.
- `glottolog.py`: Fetches and caches Glottolog metadata to `glottolog_cache.json` and `schemas/languages.yaml`; provides `is_valid_format()` and `cached_entry()`.
- `populate_sheets.py`: One-time utility for uploading legacy TSV data.
- `setup_root_folder.py`: One-time Drive folder setup (run once after first `generate-sheets`). Its own `_set_viewer_permissions` — which used to re-grant "anyone with the link" unconditionally on every run, piling up a duplicate permission on every repeat — was deleted in favour of `drive.ensure_anyone_permission`, which checks first and only creates a grant when none exists (issue #276). A second run of this command now makes zero Drive calls at all when nothing has changed.
- `generate_status_sheet.py`: Builds a locked, read-only `status_{lang_id}` spreadsheet per language in a freestanding top-level "Annotation Status" Drive folder (not nested in the project root folder, whose inherited "anyone" permission can't be removed at the child level) — one row per construction from `diagnostics_{lang_id}.yaml` with a completeness percentage, color-coded status cell, and a direct link to that construction's live tab; reuses `validate_coding.annotation_status()` for the counts and `restructure_sheets._get_pair_row_constructions()` to skip percentage computation for pair-row tabs. Shared read-only (`role="reader"`, unlike the writer share `generate_biuniqueness_allomorphy_sheet.py` uses) with `adamjamesrosstallman@gmail.com`; not yet wired into any automation — coordinator-triggered only. Migrated to the Drive doorway; the only doorway command that creates a folder with `parent_id=None` (Drive root) and the first to read *other* languages' already-existing annotation spreadsheets rather than only sheets it owns. Its own `_get_or_create_status_spreadsheet` was consolidated into `drive.get_or_create_spreadsheet`, shared with `generate_biuniqueness_allomorphy_sheet.py`'s identical copy (issue #276).
- `generate_biuniqueness_allomorphy_sheet.py`: Builds the Stage 1 biuniqueness/allomorphy screening sheet (issue #254 Part 2c), `synth0001`-only for now. Reads `Biuniqueness_Scope` (Part 2a/2b) from `planar_{lang_id}.tsv` and writes one row per (Position_Name, Element) where the scope isn't `excluded`: `filled` rows get a `has_allomorphs` y/n dropdown, `open_category` rows get a free-text `Members` column (candidates for Stage 2's not-yet-built member expansion, Part 2e). Deliberately outside the standard `diagnostics_{lang_id}.yaml`/`generate_sheets.py` class/construction pipeline — this sheet's rows are Element-keyed lexicon facts, not Position-keyed criteria feeding a `qualification_rule`; mirrors `generate_status_sheet.py`'s precedent of a purpose-built generator using `drive.py`'s primitives directly. Shared as writer with `adamjamesrosstallman@gmail.com`; coordinator-triggered only. Its own `_get_or_create_allomorphy_spreadsheet` was consolidated into `drive.get_or_create_spreadsheet`, shared with `generate_status_sheet.py`'s identical copy (issue #276).
