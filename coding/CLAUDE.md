# coding/ package structure

`coding/` contains the coordinator tooling:
- `__main__.py`: `python -m coding <command> [options]` dispatch. Every command module exposes `build_parser() -> argparse.ArgumentParser` (Phase 5 unit A/B, issue #271) separately from `main(args: argparse.Namespace | None = None) -> None` — `main()` parses `sys.argv` itself only when called with no `args`, so every existing test that monkeypatches `sys.argv` and calls `mod.main()` still works unchanged. `__main__.py`'s dispatch (`dispatch(cmd, argv)`, which `daily_refresh.py` also calls once per step) builds the parser, parses once, calls `preconditions.enforce(op_id, args)` (Phase 5 unit D), then runs `mod.main(args)` directly inside `drive_door.running(cmd, args)` instead of re-parsing inside the command — this is the chokepoint both hook into, keyed by the command name and its already-parsed `args`. (Phase 5 unit E's per-invocation `provenance.record` call was here until Phase 10 unit 5c, when the Drive door took over the log.) `restructure_sheets.py`/`sync_params.py` (hand-rolled colon/comma flag parsers) and `check_codebook.py`/`setup_root_folder.py` (no flags at all) still fit the same contract — the former's `build_parser()` exists for `--help` and unknown-flag detection while the tested colon/comma helpers still read `sys.argv` directly for values, the latter's `build_parser()` returns an empty parser. `registry.py` is the module list this file used to hand-maintain in its own docstring, now derived instead.
- `gating.py`: `flag_dest(flag)`/`gate_satisfied(apply_gate, mode_name, args)` — the one piece of gate-matching logic `preconditions.py` and `provenance.py` both need (does a record's or mode's `apply_gate` match the real args of an invocation), factored out so it isn't duplicated between them. Handles the ordinary case (space-separated `--flag` list, all must be set) and the null case (a mode with no `--apply` concept, active on its own flag alone); falls back to "always active" for a gate stated as prose rather than real flag syntax (`apply_pending`'s `apply_gate` is "interactive (per-entry approval, not a single --apply flag)", since which entries get applied depends on runtime `input()` prompts, not anything in `args`) — the safer failure mode for `writes_to_drive`, where "always active" lets the Drive door's other rules judge a real write rather than refusing every write the command makes.
- `preconditions.py`: Centralized precondition enforcement (Phase 5 unit D, issue #271) — `active_preconditions(op_id, args)`/`enforce(op_id, args)`, called from `__main__.py`'s dispatch chokepoint right after parsing, before the command's own `main()` runs. Derives which preconditions apply to a real invocation directly from that command's `data_dependency_schema/operations.yaml` record (its base `apply_gate` plus any active `modes`, matched via `gating.py`), so a precondition declared there can no longer go silently unchecked the way Findings 23/24 twice found (`docs/data-layer-progress.md`) — the declaration IS what runs, not a separately hand-written call. Only `coded_data_clean_tree` is enforced here — it replaced the scattered manual `drive._check_coded_data_clean()` calls previously in `generate_sheets.py`/`import_sheets.py`/`prune_manifest.py`/`restructure_sheets.py`/`sync_diagnostics_yaml.py`/`sync_params.py`/`update_sheets.py` (migrated file-by-file, per Jeff's decision on the unit D open question). `coded_data_git_identity_configured` and `check_notes_documents_scope_authorized` stay enforced where they already were (inside `drive._autocommit_data()`, and a manual one-time OAuth step, respectively) — neither was a "`_check_coded_data_clean()`-style call", the shape this unit was scoped to replace, so centralizing them would be a different, unscoped change.
- `provenance.py`: The provenance log, `provenance_log.jsonl` at the repo root (gitignored, append-forever per Jeff's decision on Phase 5 unit E). Since Phase 10 unit 5c the Drive door writes it (`append_writes`), from the writes themselves: when a command ends, however it ends, one line per tab or Drive file it wrote — command and arguments, file and tab, the sheet's identity, which kinds of write, how many calls and cells, and any `replacing` reason. A run that wrote nothing leaves no line. Before 5c, `record()` logged one line per invocation, at the dispatcher, from flags alone. `writes_to_drive(op_id, args)` stays here: the door asks it whether an invocation may write at all, from each command's `operations.yaml` `writes_to_drive` field (base + `modes`, matched via `gating.py`), per actual invocation — e.g. `sync-diagnostics-yaml --apply` (local only) may not write, `--to-sheet --apply` may. `apply_pending` never writes itself: its actual writes are delegated to a subprocess call to another `python -m coding ... --apply`, whose door logs them. A write a command makes even on a dry run is declared in its record's `always_on_writes` (import-sheets' pink highlighting).
- `drive.py`: Shared Drive/Sheets client helpers — OAuth2 auth, config load/save, manifest upload/download (retry on 429/500/503 is the Drive door's, `drive_door.py`), `_autocommit_data()` (commit+push writes to `coded_data/`), and `_check_coded_data_clean()` (abort if `coded_data/` has uncommitted changes matching given extensions — refuses to let a command act on a partially-written/reverted state; called only by `preconditions.py`, which runs it for every command whose `operations.yaml` record declares `coded_data_clean_tree`. Added after issue #248's stray-row incident, where `update-sheets` had no such guard and wrote bogus rows to 16 live sheets from a `planar_{lang_id}.tsv` left stale by an earlier step's failed auto-commit). Sharing helpers: project data is shared with named people only (Phase 10 unit 14) — `ensure_user_permission(doorway, file_id, email, role)` grants at least `role`, `remove_anyone_permission(doorway, file_id)` removes a link share; generated notebooks and PDF reports are the one exception and keep "anyone with the link": `ensure_anyone_permission(doorway, file_id, role="reader")` grants it unless one already exists (so a manually-revoked share self-heals and a repeat run never piles up a duplicate), and `create_or_update_shared_file(doorway, content, filename, mimetype, folder_id, existing_file_id=None, role="reader", *, identity)` (create-or-update with rename-on-update, calling `ensure_anyone_permission` — used by `generate_notebooks.py` and `generate_reports.py`). `set_user_role(doorway, file_id, email, role)` (sets a person's grant to exactly `role`, up or down, by changing it in place through the doorway's `update_permission` — Drive keeps the higher role when a lower grant is *added*, and refuses to *delete* a grant on a file that also inherits one from its folder; both checked live 2026-10-13, and the fake now models the first), `make_read_only(doorway, file_id)` (link share removed, every named editor lowered to reader; used by `prune-manifest`), and `get_or_create_spreadsheet(doorway, folder_id, name, *, identity)` (find-by-name-in-folder or create, labelled with the Drive door's `identity` — used by `generate_status_sheet.py`). The old hardcoded, uncollapsed sharing helpers `_share_anyone_with_link`, `_share_with_person`, and `_remove_anyone_permission` were dead code (no remaining callers once the doorway migration finished — every caller that used to reach them directly now goes through the doorway instead) and were deleted rather than folded in — see `docs/data-layer-progress.md`'s decisions log. `upload_manifest()` checks the config it's about to write against `manifest_contract.check()` (Phase 6 boundary 4, issue #271) and prints a warning if it finds anything, but writes regardless — deliberately non-blocking; see `manifest_contract.py`'s module docstring and `docs/data-layer-progress.md`'s 2026-08-17 decisions-log entry for why.
- `manifest_contract.py`: pydantic data contract for the Drive manifest (Phase 6 boundary 4, issue #271) — the plan's fourth candidate boundary, and the odd one out: dict/JSON, not a DataFrame, so pydantic rather than the pandera `planars/contracts.py` and `contracts.py` use. Far more permissive than the other three boundaries and never raises — `check(full_config)` returns a list of problem strings (empty if none). `load_manifest()` is the highest-blast-radius function in the project (called by nearly every command), and this model can only be checked against one static fixture (no live Drive access before Phase 9), so every field is `Optional` and `extra="allow"` at every level — a violation means the manifest isn't shaped like `{lang_id: {...}}` at all, not merely that it carries an unrecognized field. Two callers: `drive.upload_manifest()` (warns, never blocks) and `integrity_check.py`'s `MANIFEST SHAPE` section (does let a violation drive a real, trackable `integrity-error` — safe given how permissive the model is). See the module docstring for the full reasoning.
- `drive_doorway.py`: The Drive/Sheets **doorway** — the one interface commands should use to reach Drive, Sheets, and Docs (issue #271, Phase 0a). Defines the `DriveDoorway`/`SpreadsheetHandle`/`WorksheetHandle` protocols, `GspreadDoorway` (live), and `get_doorway()`/`set_doorway()` for injection. Handle method names mirror gspread's exactly, so migrating a caller is a call-site substitution and helpers shared with unmigrated files keep working; `GspreadDoorway` therefore returns raw gspread objects as handles, but commands never hold them: `get_doorway()` and `set_doorway()` wrap every doorway in the Drive door (`drive_door.py`, below). `tests/fake_drive.py` is the offline implementation, seeded from `coded_data/.test_fixtures/drive_state/` (recorded by `capture-drive-state`; in planars-data because it is real annotation content) — it makes every command testable with no network and records a mutation log for assertion. Command tests read local files from the matching frozen copy, `coded_data/.test_fixtures/coded_data/` (`fake_drive.FROZEN_CODED_DATA`, or `use_frozen_coded_data()` to redirect every module's `CODED_DATA` to a private copy of it; a harness that builds its own copy uses `point_coded_data_at()`, never one module's `CODED_DATA` alone, since the Drive door reads its own), never from the live language folders, which change whenever an annotator works. **Migrated so far: `refresh_dropdowns.py`, `generate_reports.py`, `setup_root_folder.py`, `apply_pending.py`, `prune_manifest.py`, `check_notes.py`, `sync_diagnostics_yaml.py`, `import_planar.py`, `generate_notebooks.py`, `update_sheets.py`, `generate_status_sheet.py`, `validate_coding.py`, `integrity_check.py`, `import_sheets.py`, `sync_params.py`, `generate_sheets.py`, `restructure_sheets.py`, `locked_tabs.py`, `annotator_notices.py`.** All commands that touch Drive now go through the doorway (`tests/test_doorway_coverage.py` derives the list and confirms it is empty, and checks the list above against the code, so no count is kept here by hand; the plan's hand-written count of eleven was wrong). `tests/render_mutations.py` renders a mutation log into a reviewable digest (tab titles and column headers resolved instead of raw IDs) — use it for the human-review step, not the raw JSON; it cannot yet resolve headers for a spreadsheet created within the same test run (only recorded fixtures), so a creation-heavy digest like `generate_sheets`' or `restructure_sheets`' shows `BEYOND HEADER` throughout — a rendering gap, not a migration bug, confirmed by the mutation-log diff instead. `tests/mutation_checks.py` holds assertions shared across commands; so far one, `assert_no_criterion_writes_onto_trailing_columns` — no dropdown and no criterion note may land on `Source`/`Comments`. Two commands got that wrong independently (#272 and Finding 10), and `sync_params.py` — the file that inserts and deletes criterion columns most densely of any command — was checked against the same list and passes it clean: `_get_current_params`, `_insert_param_columns`, and `_build_dropdown_refresh_requests` all derive a tab's criterion columns from its own header, never from the manifest. `generate_sheets.py` was the other file flagged for this check (it builds `construction_params` and per-column dropdowns directly from the diagnostics YAML in `_create_analysis_sheet`, `_add_constructions_to_existing_sheet`, and `_regen_construction`) and also passes clean: every dropdown/note write derives its column position from the row it just built, never from a stored manifest offset. `generate_status_sheet.py` reads a same-named but unrelated local `_construction_params()` — not the manifest's — and `validate_coding.py` writes only pink highlighting built from its own local param map, so neither ever needed that assertion. `integrity_check.py`'s `_section_sheets` and `import_sheets.py`'s `_validate_tab`/`_validate_pair_tab` both also read `construction_params`, the former to *compare* it against the live header and print a warning on mismatch, the latter as the allowed-value set fed into validation — neither ever writes a dropdown or a criterion note back to Drive (`import_sheets.py`'s only sheet write is `highlight_cells`, painting backgrounds), so neither needed the assertion; see the mismatch-comparison bug recorded as a Finding in `docs/data-layer-progress.md`, unrelated to the migration itself. `restructure_sheets.py` caught a real, pre-existing bug this way (Finding 16, `docs/data-layer-progress.md`): `_copy_pair_tab_with_rename` hardcoded `col_start=4` for a re-populated pair tab, right for coreference's four-structural-column shape but wrong for nonpermutability's/phrasal_accent's two-column "general" shape, landing the dropdown on `Comments` instead of the criterion column. Confirmed identical between the unmigrated and migrated code (pre-existing, not introduced by the migration) before being fixed in a follow-up commit the same day — `col_start` is now `header.index(criterion_col)`, derived rather than assumed, matching every other column-writing function in this file.
- `drive_door.py`: The Drive door (Phase 10 unit 5, issue #271; design `docs/drive-door-design.md`). `get_doorway()` wraps whichever doorway is installed in `CheckedDoorway` (live: watch mode, `LIVE_MODE`; tests' `set_doorway(fake)`: enforce). Its handles have only the protocol's methods, and every write is checked first: the command may write at all (`running(command, args)`, called by `__main__.py`; `operations.yaml` decides, with `always_on(name)` for a declared `always_on_writes` write; no command running = refused); the `batch_update` request type is in `REQUEST_TYPES`; and for a class sheet, the rules from `sheet_spec.py` — an annotator's filled cell is never changed or lost except inside `replacing(tab, reason)`, locked tabs get only their builder's content, dropdowns only on criterion columns with the spec's values, protection only on locked tabs, sharing only with the language's annotator by name (writer while live, reader once labelled archived). Every call is retried on 429/500/503 here and nowhere else; a create is retried only after checking the first attempt didn't land. **Identity labels (unit 5d):** every file the tooling makes carries Drive properties saying what it is (`planars_kind`/`_lang`/`_class`/`_name`, `planars_state=archived`; kinds in `KINDS`, built with `class_sheet`, `lang_file`, `manifest`, `notebook`, `folder`), and every create on the door requires `identity=`; `mark_archived` is called where class sheets are archived (`restructure_sheets._lock_archived_sheet`, `prune_manifest._archive_drive_sheet`) and undone by `_rollback_unit`. Each tab of a class sheet carries developer metadata (`planars_tab_kind`, `planars_tab`), written at the end of any successful writing command for the class sheets it wrote, so a tab renamed by hand is still recognised. The door places a file from what the command made, then its label (files made before 5d were labelled by `migrations/label_drive_files.py`, 2026-10-15, and the manifest fallback was then deleted); writes to anything it can't place pass unchecked by the class-sheet rules. **Rule 6 (unit 5d):** at the end of a command that succeeded and was allowed to write, each class sheet whose shape it changed (values, rows, columns, tabs, protection — not formatting, dropdowns or highlights) is re-read and compared with its spec: tab names, order and protection, and each written tab's columns and row keys (pair rows from `generate_sheets.pair_rows`, keyed rows from `biuniqueness_rows.keyed_rows`, via `sheet_spec.expected_row_keys`). The door remembers each sheet and tab as it was before the command first wrote to it, and reports only mismatches that are new, so drift already there (which has its own `sheet-drift`/`planar-changed`/`dependent-stale` issues) is never blamed on the command. A sheet made to replace another (`create_spreadsheet(..., replaces=old_id)`, restructure-sheets) takes the old sheet's tab list as its "before", and its carried-over pair and keyed rows are left to the dependent-stale check. In watch mode a broken rule lets the write through and the command files one `door-violation` issue at the end. Since unit 5c the door also does three things commands used to do for themselves: `replacing(tab, reason, kept=..., allow_drop=...)` re-reads the tab and reports an annotator's mid-run edit (comparing with what the command read earlier in the run), saves the tab to `SNAPSHOT_DIR` (`regen_snapshots/`, one file per tab, overwritten), and, given the row keys the rebuilt tab keeps, raises `AnswersWouldBeDropped` — in every mode, before anything is written — if an answered row (any criterion, Source or Comments cell filled) would be lost; and at the end of a command it writes one provenance line per tab or file written (`provenance.append_writes`). Tests' `provenance_log.jsonl` and snapshots go to each test's `tmp_path` (`tests/conftest.py`). Tests run commands through `tests/command_runner.run_command`, which says which command is running; `tests/test_drive_door.py` tests each rule.
- `registry.py`: `python -m coding registry` — the derived command inventory (Phase 5 unit C, issue #271). `build_registry()` joins two things that already exist and were never duplicated into this file: `__main__.py`'s `_COMMANDS` table plus every command module's `build_parser()` (Phase 5 units A/B — what flags a command takes) with `data_dependency_schema/operations.yaml` (Phase 4 — what a command does, its side effects, idempotency, preconditions). Recomputed fresh on every call, nothing cached, so there is nothing here that can go stale — the plan's own words for why this has to be derived rather than hand-authored: "a hand-authored registry is worse than none, because a stale map gets trusted." **That claim was false until 2026-08-18** (Phase 8, issue #271's idempotency audit): `_load_operations()` cached the parsed `operations.yaml` in a module-level global after its first read — harmless for the ordinary CLI invocation (a fresh process every time) but a real gap for anything importing this module and calling `build_registry()` more than once in the same process, which a test suite does constantly. Fixed by removing the cache; `tests/test_registry.py`'s `test_a_second_call_in_the_same_process_reflects_a_changed_operations_yaml` proves it directly (writes a real file, calls twice, changes the file in between, confirms the second call sees the change) rather than trusting the docstring. Plain listing by default (`cli_command` + `operations.yaml`'s `description`, one per line); `--command CLI_COMMAND` for one command's full detail (flags, side effects, idempotency, preconditions, whether it writes to Drive, modes). Replaced `__main__.py`'s own hand-maintained "Commands:" docstring table, which was exactly the kind of duplicated inventory this command exists to remove.
- `capture_drive_state.py`: Records live Drive state (spreadsheets + manifest) to `coded_data/.test_fixtures/drive_state/` and, at the same moment, freezes each captured language's local folder to `coded_data/.test_fixtures/coded_data/` — the two halves the command tests run against, always replaced together (`--lang` keeps the other languages' entries; a captured language's recording of a sheet no longer in the manifest is deleted). Both live in planars-data, which is private, because they are real annotation content. **Read-only** against Drive — the only live Drive call permitted before Phase 9 of the data layer plan. Never normalise or hand-edit the fixtures; re-run the capture instead, then regenerate the saved test outputs, review, and commit inside `coded_data/`.
- `refresh_dropdowns.py`: Refreshes criterion dropdown validation on existing sheets without touching annotation data (`--apply`, `--lang`); reads criterion columns from the tab's own header and values from the diagnostics YAML, never the manifest (issue #272's fix — see `_resolve_criterion_columns`/`_fresh_param_values`). Its manifest write now goes through `drive.upload_manifest`, the same shared writer `generate_sheets.py`, `sync_params.py`, `update_sheets.py`, `import_sheets.py`, and `restructure_sheets.py` already use, instead of an inline `doorway.update_file` call with no key-reordering and no create-if-missing fallback — closing the gap where a lost `_planars_config_file_id` meant it gave up with a `[WARNING]` instead of creating a fresh manifest.json like every other writer (issue #276).
- `schemas.py`: Cached loaders for `load_diagnostic_classes()` and `load_diagnostic_criteria()`; `languages.yaml` excluded (read fresh by callers). Also the one reader of a tab's criteria (`criteria_for`) and of `diagnostic_criteria.yaml`'s `value_placeholders` (`placeholder`, `placeholder_kind`, `free_entry_kind`, `is_free_entry`; an undeclared `<...>` value raises).
- `make_forms.py`: `build_element_index`, `_read_diagnostics_for_language` — utilities used by other scripts. `_load_diagnostics_yaml_for_edit`/`_dump_diagnostics_yaml` are the one way a command changes a diagnostics YAML (ruamel.yaml, so comments, quoting and layout survive; an unedited file comes back byte-for-byte). Also provides `resolve_keystone_active` and `resolve_keystone_na_criteria`. Handles `construction_criteria` — emits one TSV row per construction for classes that use it. `build_element_index`'s Position/Class_Type validation is enforced via the pandera schemas in `contracts.py` (Phase 6 of the data layer redesign, issue #271), not inline `if`/`raise` blocks; it catches `pandera.errors.SchemaError` and re-raises `ValueError` so its three callers (`generate_sheets.py`, `update_sheets.py`, `restructure_sheets.py`) see the exception type they always have.
- `contracts.py`: pandera data contracts for `make_forms.py`'s planar-load boundary (Phase 6 of the data layer redesign, issue #271, second of four candidate boundaries — see `planars/contracts.py` for the first). `position_integer_schema()` and `class_type_schema()`. See the module docstring for the two-stage narrowing this reproduces and why the duplicate-key check stays procedural.
- `generate_sheets.py`: Creates annotation sheets; validates planar/diagnostics first; **dry-run by default — the base (sheet-creation) command requires `--apply` to write anything to Drive** (`_plan_language_creation` computes what would be created from already-fetched manifest data, no live Drive calls needed for the dry-run report itself). This was a gap until this convention was regularized: unlike every other mutating command in the project, `generate-sheets` previously had no dry-run/apply distinction at all and always wrote live — fixed after an accidental live-sheet creation surfaced the inconsistency with `docs/tooling-design.md`'s "dry-run by default" principle. `--regen-construction` and `--regen-dependents` are separate code paths, unaffected by `--apply` — they always act live, gated by their own guards instead (see below). **`--force` aborts if any language already has sheet IDs in the manifest** (annotation data is irreplaceable); each spreadsheet gets a `Status` tab with `in-progress`/`ready-for-review` dropdowns. Supports two-stage pair-sheet workflows for **nonpermutability** (`element_prescreening` first, then `--regen-construction nonpermutability:general`) and **coreference** (`prescreening` first, then `--regen-construction coreference:reflexivization` etc. for each pair construction). Both prescreening filters (`_filter_nonperm_pairs_by_prescreening`'s `scopal`, `_filter_reflex_pairs_by_prescreening`'s `referential`) exclude an element **by name, across every structural position**, not just at the one position marked `n` — an unresolved linguistics question (is the criterion a property of the element globally, or of the element at a position?), not a bug to silently pick a side of. Both now share `_abort_if_criterion_diverges_by_position`, which aborts and files/updates a `diagnostics` GitHub issue when an element is marked `n` at one position and `y`/`both` at another, rather than resolving it either way. First built for `scopal` (issue #228); `referential` didn't get the same guard until issue #285 found the gap — #228's own text had incorrectly assumed coreference was unaffected. `_regen_dependents_simple` runs automatically during `data-refresh`, gated by `coded_data_clean_tree` first (enforced centrally — see `preconditions.py`'s entry above) — but only ever fills a dependent tab with no rows (nothing to lose): one that doesn't exist yet, or one that exists but is empty once its source tab is marked `ready-for-review` in the Status tab (the hand-off annotators are told about; added 2026-10-12, #254, after biuniqueness's empty morphemes tab turned out to be invisible to every check). Never one with rows, so it can't hit the guard below. Pass `--pos-remap OLD_NUM:NEW_NUM` (repeatable) when position numbers have shifted. **`--regen-construction` aborts instead of writing if it would silently drop an answered row** (since Phase 10 unit 5c the Drive door's check: `_rebuild_tab` passes `drive_door.replacing` the keys of the rows it carries over, `kept`, and turns `AnswersWouldBeDropped` into the abort; a coreference `--pos-remap` passes the old keys via `_coreference_key_map`; until 5c this was `_find_annotated_drops`, which looked only at the first criterion column) — it overwrites the live Sheet immediately with no confirmation step downstream (`import-sheets` → `apply-pending` only syncs the *local* copy to match afterward, it doesn't gate the write). Run `restructure-sheets --split-element`/`--rename-element` first if the element was renamed or split (clears the guard naturally, since the old rows are already gone from the Sheet by the time `--regen-construction` runs — no need to remember command order), or pass `--confirm-drop` if the drop is a genuine scope change, not data loss. See issue #241. Rows are matched by the key the schema declares for the tab (`planars.schema_values.row_key`; `_pair_key`), and since 2026-10-13 a tab whose columns aren't the shape the schema gives it is refused too (its answers couldn't be matched), unless `--confirm-drop`. **Before `--regen-construction` clears and rewrites a tab, the Drive door saves its live content to `regen_snapshots/{lang}_{class}_{construction}.json` (gitignored)** (issue #271, a Phase 7 follow-up; `_snapshot_before_regen` here until Phase 10 unit 5c moved it into `drive_door.replacing`). The tab read exists to preserve live annotator edits not yet downloaded via `import-sheets`; the clear-then-rewrite is two separate Drive calls, not atomic, so a crash between them could otherwise destroy them. A plain snapshot, not a resume system: re-running `--regen-construction` after any interruption recomputes the rows from source data; the snapshot is for checking by hand whether anything was lost, and is overwritten each run. Migrated to the Drive doorway — the largest file migrated so far (2,654 lines) and the first whose migration was not a plain call-site substitution in `main()`/one leaf helper: `gc`/`drive` were threaded as explicit parameters through this file's own call chain (`_create_or_update_tsv_sheet` → `_upload_lang_setup_as_sheets`, `_create_analysis_sheet`, `_regen_construction` → `_regen_dependents_simple`), so the migration replaced two parameters with one (`doorway`) at every level. `_add_constructions_to_existing_sheet` needed no signature change at all — it already took an open spreadsheet handle rather than a client, since `update_sheets.py` (which also calls it) reaches Drive through the doorway with no client to hand over. `_regen_construction`'s spreadsheet open now retries where it previously did not (opening is an idempotent read, so this changes nothing about what gets written) — see `docs/data-layer-progress.md`'s decisions log. **`--apply` used to skip a language's existing-class-new-construction scan whenever that language also had a brand-new class with no sheet at all** — the scan only ran inside the `if not new_class_names` branch, so a class that already had a sheet but gained a construction in its diagnostics YAML was silently left behind on any run that also created a new class sheet. Found onboarding arao1248's `nonpermutability`/`free_occurrence` classes (2026-08-10) when its unrelated `subspanrepetition` construction addition stopped showing up in the same run. Fixed by running the scan unconditionally over every already-existing class, independent of `new_class_names`. Retry on every call is the Drive door's (`drive_door.py`; issue #284's per-call wrappers were removed in Phase 10 unit 5b). `--regen-construction` rewrites a tab inside `drive_door.replacing()` (`_rebuild_tab`), having carried every answer over by key. **`_regen_dependents_simple` now returns the list of (language, dependent construction) failures instead of `None`, and `--regen-dependents` exits non-zero if that list is non-empty** (issue #283, 2026-08-19) — a per-language regeneration failure was already caught and printed, but otherwise vanished with no way for the caller (or the daily automation) to know anything had gone wrong; `data-refresh.yml` now files/closes a `regen-dependents-error` issue keyed on the exit code. One failure still doesn't stop the loop from trying the rest — that per-item resilience is this function's whole contract, unchanged.

That collapse surfaced a real, pre-existing bug: this file's viewer-grant reassertion had no existence check, so every regeneration (which happens after nearly every `--apply` across several commands) silently added another duplicate "anyone" permission — the same bug `setup_root_folder.py` had, just never compared side by side before. Fixed by the same `ensure_anyone_permission` check that fixes `setup_root_folder.py`. `drive_config.json` is saved after every individual notebook upload, not once after all four upload loops — fixed 2026-08-11 (issue #280): a crash partway through used to leave earlier successful uploads' new file IDs unpersisted, so a retry created duplicate files instead of updating the existing ones.
- `generate_reports.py`: Generates and uploads `report_{lang_id}.pdf` directly (no Colab; used by nightly GitHub Action). Uses `drive.create_or_update_shared_file` for the upload (its own `_upload_pdf` was deleted) — before issue #276 this file shared its "anyone" grant only on create, so a manually-revoked report share was never restored, unlike a notebook's; both now reassert every run through the same idempotent `ensure_anyone_permission` check, so a report share self-heals too, without duplicating on a normal repeat run. `drive_config.json` is saved after every language, not once after the whole loop, and a PDF-rendering failure on one language no longer aborts the run for every language after it — both fixed 2026-08-11 (issue #280), same reasoning as `generate_notebooks.py` above.
- `check_codebook.py`: Consistency check between diagnostic_criteria.yaml, diagnostic_classes.yaml, analysis modules, and diagnostics_{lang_id}.tsv.
- `integrity_check.py`: Full project-wide health report; `--lang` restricts per-language sections; `--sheets` includes live Sheets structural validation. Its DEPENDENT CONSTRUCTION STALENESS section checks pair-row constructions against their prescreening source two ways: element identity (pre-existing) and, since issue #241, position number (`_find_stale_position_cells`/`_suggest_position_remap`/`_planar_position_names`) — a pair-row can be element-identity-correct and still reference a position number superseded by a structural change elsewhere in the planar, invisible to element-set comparison alone (discovered when stan1293's coreference pairs turned out to reference pre-`v:obj-R`-insertion position numbers, apparently since the sheets were first generated). When recoverable, prints ready-to-use `--pos-remap` flags for `generate-sheets --regen-construction`. For both `nonpermutability` and `coreference`, the "in scope" element set is computed element-level (excluded everywhere if *any* position was marked `n`), matching `generate_sheets.py`'s real filters exactly — it used to approximate `coreference` differently (any single non-`n`/`na` row was enough to count an element as in-scope, a union rather than the real filter's exclusion), producing a false "stale" report for any element marked `referential=y` at one position and `referential=n` at another. Found and fixed as issue #285. Migrated to the Drive doorway; its footprint is two independent read-only entry points (`--sheets`' spreadsheet-open/list-worksheets/read-header sequence, and `--check-manifest`'s manifest-only fast path) — no writes anywhere in the file. Its `MANIFEST SHAPE` section (`_section_manifest_shape()`, part of the default report) checks the live manifest against `manifest_contract.py`'s pydantic model and, unlike `upload_manifest()`'s non-blocking version of the same check, lets a violation contribute to `total_e` and drive a real `integrity-error` issue (Phase 6 boundary 4, issue #271) — safe to do only because the model is deliberately permissive, so a violation here means something structurally broken, not an unrecognized field.
- `glottolog.py`: Fetches and caches Glottolog metadata to `glottolog_cache.json` and `schemas/languages.yaml`; provides `is_valid_format()` and `cached_entry()`.
- `setup_root_folder.py`: One-time Drive folder setup (run once after first `generate-sheets`). Since 2026-10-12 (Phase 10 unit 14) it *removes* any "anyone with the link" grant from the root folder (`drive.remove_anyone_permission`) instead of granting one: every language folder inherits the root's sharing, and project data is shared with named people only. Before that it granted link access (and, before issue #276, re-granted it on every run). A second run makes zero Drive writes when nothing has changed. Retry is the Drive door's (since Phase 10 unit 5b), and the door retries a create only after checking the first attempt didn't land, so a lost response no longer risks a second root folder.
- `generate_status_sheet.py`: Builds a locked, read-only `status_{lang_id}` spreadsheet per language in a freestanding top-level "Annotation Status" Drive folder (outside the project root folder, so status sheets can be read-only for annotators while the annotation sheets beside them are editable) — one row per construction from `diagnostics_{lang_id}.yaml` with a completeness percentage, color-coded status cell, and a direct link to that construction's live tab; reuses `validate_coding.annotation_status()` for element-row counts and `validate_coding.pair_annotation_status()` for pair-row tabs (nonpermutability's `general`, coreference's three) — `restructure_sheets._get_pair_row_constructions()` only decides which of the two to call; both feed the same completeness percentage, re-read from the live sheet every run so it tracks pair-row regeneration automatically. Shared read-only (`role="reader"`) with each language's annotator by name (`coding/people.py`; addresses live in private planars-data); rebuilt daily by `data-refresh.yml` (after `update-sheets`; a failure files `status-sheet-error`) since 2026-10-14, when Adam saw 89% on tabs he had finished because nothing had rebuilt it. A class spreadsheet it cannot open (shown as "could not open sheet") or a diagnostics file it cannot read counts as a failure: the run finishes the other languages, then exits non-zero naming each one (until 2026-10-14 the first was a printed warning nobody saw). Migrated to the Drive doorway; the only doorway command that creates a folder with `parent_id=None` (Drive root) and the first to read *other* languages' already-existing annotation spreadsheets rather than only sheets it owns. Finds or creates each status spreadsheet with `drive.get_or_create_spreadsheet` (issue #276). Retry on every call is the Drive door's (`drive_door.py`).
- `biuniqueness_rows.py`: Row building for the `biuniqueness_deviations` class sheet (issue #254), logic only — `generate_sheets.py` dispatches here for this class and does the writing. Three tabs, each generated from the one before, their names read from the schema's `depends_on` chain (`planars.biuniqueness_deviations.ELEMENTS_TAB`/`MORPHEMES_TAB`/`MORPHS_TAB`, re-exported here as `ELEMENTS`/`MORPHEMES`/`MORPHS`; `sources_of`/`keyed_rows` are the one statement of which tab feeds which): `elements` (standard element rows, but only elements in scope — computed from `Elements` by `make_forms.classify_biuniqueness_scope`; the planar's stored `Biuniqueness_Scope` copy was deleted 2026-10-13 — with `has_allomorphs` pre-set `NA` on open-category rows), `morphemes` and `morphs` (the project's first **`row_type: keyed_rows`** tabs: rows identified by the `keyed_columns`/`key` the schema declares, read everywhere through `restructure_sheets._get_keyed_row_constructions()`, which also hard-fails on an unknown `row_type` or a keyed construction missing its columns). `carry_over()` is the regeneration rule: answers follow their row by key and always beat a generated pre-fill; a row with no `Origin` was added by hand, is marked `hand-added`, and survives every rerun; a generated row whose source is gone is left out — if it was answered, the Drive door refuses the rewrite unless `--confirm-drop` (`carry_over` returns `(rows, counts)`; the rows' keys go to `drive_door.replacing` as `kept`). Every command that branches on row shape handles keyed tabs explicitly: `generate_sheets` (create, add, `--regen-construction`, `--regen-dependents` via `staleness_check: keyed_source`), `validate_coding` (`validate_keyed_rows`, `keyed_annotation_status`; `blank_ok_when` rules), `import_sheets`, `update_sheets` (keyed tabs left to regeneration; the elements tab adds only in-scope rows), `restructure_sheets` (keyed tabs copied with position/element renames; split elements flagged for review; `--rename-class` refuses classes with pair or keyed tabs), `generate_status_sheet`, `integrity_check` (`_keyed_staleness` in the dependent-staleness section), `sync_params`, and `tests/make_synthetic_lang.py`. Criteria whose allowed values are only placeholders — `<free_text>`, `<position_names>` — are free entry: no dropdown (`coding.schemas.is_free_entry`), kept exactly as typed (never lowercased), may be blank, and `<position_names>` values are checked against the planar.
